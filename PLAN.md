# Standalone PayPal service: backend and checkout refactor

Updated and reviewed: 2026-10-23. Implementation authorized on refactor/local-direct-checkout.
The provider checkpoint passed after the user corrected the Sandbox merchant. The direct-flow refactor is implemented; see docs/VERIFICATION.md for checks and docs/INTEGRATION.md for remaining merchant-specific verification.

Confirmed by the user: this service has no historical data or records to preserve. Build one clean target schema and API; there is no backward-compatibility API requirement. Existing local records created since implementation retain their identities through schema migrations. Remove role management entirely. All authenticated staff have the same access level.

## Unified payment register

Use a single Payments page and payments table for all payment lifecycle states. No separate request page, table, model or compatibility routes. Immutable payment_attempts, subscriptions and financial transactions reference payment_id. Each individual collection belongs to one payment; refunds/reversals are ledger entries linked to that collection and payment, never extra top-level payments. Subscription installments each have their own payment, distinct from subscription activation. Imported collections create payment rows without fabricated operator intent or billing metadata. The collected/refunded filter acts on payment outcomes, including partial refunds; Checkout result filters terminal Success/Failed independently of financial state.

## 1. Target and boundaries

The operator enters the required First name, Last name and Agreement number together with payment terms, presses Submit, enters card details in PayPal-controlled UI, and receives the verified result in the local dashboard. Customers do not access this internal service.

Run one FastAPI process, the existing React dashboard and PostgreSQL locally at http://localhost:8100. Keep the RuTV appearance. No remote deployment, company-site changes, tunnel, public webhook, local certificate setup or Live enablement. Requests to PayPal itself use HTTPS. Prove that the selected Sandbox checkout product accepts local HTTP and its return URLs; do not assume every product does.

Retain the requested one-time payments, subscriptions, permitted refunds, search/statistics and explicit read-only imports/synchronization. Support exactly ILS, USD and EUR. These functional requirements do not preserve the old execution architecture.

No periodic polling of PayPal, the operation queue or frontend status. No background worker, scheduled retry, startup replay, recovery subsystem, SSE, websocket, automatic SDK/API fallback or backward-compatibility execution path.

Payment-attempt rule: one explicit operator Submit creates a new payment, immutable attempt, intent key and provider mutation identities. Approval-to-capture may execute once. Checkout ends as success after verified PayPal approval/completion, or failed after cancellation, error, abandonment or unsuccessful creation. Checkout results are terminal: a failed checkout is never resumed or promoted by later callbacks/reads. PayPal-managed recurring billing, installment retries and outcome emails remain PayPal responsibilities.

Wait for the current request to receive its answer before allowing another payment attempt. Disable new-attempt/navigation controls during open API requests and reject overlapping checkout mutations per operator on the backend, including across browser tabs. After the answer arrives, Create payment opens an empty form; prior saved provider/checkout states do not block it. Each accepted new Submit atomically closes all unfinished local checkouts belonging to that operator as failed before saving the new attempt. Never automatically cancel a provider subscription, erase collections or release refund reservations. An old intent cannot be reused; duplicate delivery of its original key returns the saved result. Each new Submit uses fresh intent/submission/provider identities. No identity is created merely by opening a form.

Each attempt owns an immutable snapshot of its client/agreement metadata and terms. Disable editing during its active checkout. Leaving it closes the local checkout as failed and destroys the hosted session. The next form is independent and cannot rewrite prior terms.

The reference interaction is create -> PayPal approval -> server capture -> display result. Adapt it to Python and persisted financial records; do not copy demonstration in-memory storage, unbounded timeouts or raw error logging.

First implementation checkpoint, before rewriting the payment path:

- Verify the configured merchant's supported operator-assisted card flow and availability for ILS/USD/EUR. API/SDK eligibility alone does not prove every merchant/product capability or guest recurring capability. Existing-service source is useful if available, not a prerequisite or architecture to copy.
- Prefer the supported PayPal-hosted guest/card experience that meets the embedded requirement. Never put an arbitrary PayPal approval URL inside an iframe or create a second application to wrap the SDK.
- Verify that the supported SDK trigger can act as Submit with the required user gesture, local HTTP and callback URLs. Initialize the chosen SDK before enabling Submit.
- Prove that the chosen SDK opens from the original Submit gesture even when order creation is asynchronous. Use that SDK's documented launch sequence; do not wait for a fetch and then assume window.open will escape popup blocking. Hosted redirect, if selected, uses top-level navigation. This requires no extra operator Open PayPal button.
- Verify that the selected SDK exposes the payment failure/cancellation outcomes needed to end an attempt. Once such an outcome is delivered, close/unmount the payment session and show the recorded result; do not call SDK restart/resume/submit again or programmatically correct and resubmit. Do not promise control over undisclosed PayPal-hosted internal processing; document any product limitation before selecting it.
- Select one SDK version, initialization method and presentation. If embedded checkout is unsupported, record the reason and select the permitted hosted redirect alternative before coding it. Do not implement both as speculative runtime fallbacks. If no supported product meets the workflow, report that blocker instead of inventing one.

Distinguish normal SDK redirect return handling from retrying a failed payment. If the selected SDK requires hasReturned()/resume() to dispatch the initial return callback, allow it only for that still-open original attempt and only before any outcome mutation has been claimed. It must never reopen a failed/cancelled session or repeat create/capture. If raw hosted redirect handling is selected instead, do not also implement SDK return handling. See [PayPal redirect return handling](https://developer.paypal.com/sdk/js/reference/#paymentsessionresume).

The implementation must follow the chosen SDK's actual outcome contract. Embedded checkout normally supplies browser SDK callbacks/results; our browser handler POSTs to the local backend. Redirect checkout supplies approval-return/cancel navigation. Neither supplies a guaranteed server-to-server success/failure notification for every card attempt. Approval is not collection, cancellation is not decline, and some input/3DS errors remain inside PayPal UI.

## 3. Backend: direct requests, simple responsibilities

Use ordinary async request handlers and direct function calls:

- main.py: routes, shared HTTP client, startup migrations, ownership and readiness.
- services.py: checkout/completion/refund/subscription decisions and short transactions.
- paypal.py: provider requests, on-demand OAuth caching, bounded timeouts and safe errors.
- models.py/db.py: durable financial records, constraints and request-scoped sessions.
- normalize.py/reporting.py/serialization.py: retain only functions actually used by direct actions or reports.

No new provider interfaces, abstract repositories, dependency-injection framework, generic command bus, workflow engine, plugin registry or event framework. Use small typed functions; split files only for concrete responsibilities. Keep login/session protection and simplify authentication by removing role management. Do not rewrite reporting merely to make the refactor larger.

For each provider mutation: commit the immutable terms, action identity and reservation; release the transaction; make the outbound request; then commit the verified result. Never hold database transaction/row locks over PayPal HTTP. Set coherent provider/request timeouts. Request cancellation or a timeout does not prove the provider rejected a mutation.

Design the target schema solely for the new direct flow: payments/attempts, resulting financial records, subscriptions and the minimum persisted action identity/reservation fields needed to prevent duplicate charges/refunds. Do not preserve the old operations/job or webhook-inbox schema, queue columns, retry metadata, historical mappings or archive models. Reuse code only when it directly serves the target design; reuse of the old table layout is not a requirement. Records created after the refactor must still persist real outcomes and idempotency identities.

Preserve Decimal/NUMERIC money, separate currencies, stable provider idempotency keys, unique provider identities, refund reservations, staff authentication, CSRF/origin checks, environment/merchant ownership and safe audit logs. These protect actual mutations; they are not fallback/recovery features.

Keep startup migrations and one-process database ownership. Before mutations and in readiness, verify the pinned ownership connection without transparently reacquiring a lost lock. Loss of ownership disables mutations until restart. No periodic heartbeat or task-dependent readiness remains.

## 4. One staff access level; no role management

Keep authenticated internal access, existing configured staff credentials, password hashing, signed sessions, logout, CSRF/origin checks and private health/API endpoints. Every authenticated staff account has the same access to the supported functions. Operator describes the person using the app, not a permission role.

Remove viewer/operator/admin role distinctions, role fields in configuration and request/response models, role-based dependencies/checks, permission maps, role-based UI visibility, role labels, role editing and role-specific tests/documentation. Apply the same simplification to configured trusted API credentials if that entry point is retained. Remove role fields from AUTH_USERS/API_KEYS examples and from the local credential configuration during implementation while preserving the credential identities and hashes. Do not keep a default-role property, ignored role key, compatibility alias or always-operator adapter. Existing sessions may require a fresh login under the new single-access contract; do not retain two session/principal formats.

No account administration UI, groups, ACL framework or replacement permissions subsystem is needed. Keep a simple authenticated staff identity for attribution/idempotency and one authentication dependency for protected routes.

Minimal browser authentication flow:

1. On initial app load, call GET /api/v1/auth/me once. A valid session opens the dashboard; 401 shows the login form. A network/server error is displayed as unavailable, not misreported as invalid credentials. No periodic session checks.
2. The operator enters username/password once. POST /api/v1/auth/login verifies the configured password hash, sets one signed HttpOnly session cookie and returns the staff name plus CSRF token. Open the dashboard directly from that response; do not add another /me request or permission lookup after login.
3. Same-origin requests send the cookie automatically. The API helper adds the CSRF token to mutations; one shared authentication dependency validates the session and mutation origin/CSRF. No separate operator guard or background-worker check belongs in authentication.
4. POST /api/v1/auth/logout clears the cookie and local identity/CSRF state. Expiry requires an explicit login. Never automatically replay a payment after login, an auth error or reconnection.

Keep only login, me and logout as browser-auth endpoints. Use configured username-to-password-hash entries with no user table, role object, registration, password-reset workflow or account-management screen. Keep the existing fixed session lifetime and simple failed-login limit; no remember-me option, refresh endpoint, refresh tokens, token rotation service or session database. Read passwords only during login and never retain them in browser storage. The browser keeps identity/CSRF in memory; a reload obtains them through /me. Password/credential changes invalidate prior sessions using the existing simple credential-version check.

Use one host consistently: http://localhost:8100 for the dashboard and callbacks. Do not switch to 127.0.0.1 during checkout, because host-only cookies do not move between those hosts. Set the staff cookie explicitly to SameSite=Lax, HttpOnly, Path=/ and no Domain; use the existing local Sandbox cookie setting. Lax supports a top-level GET return from PayPal without requiring another login, while mutation POSTs still require same-origin CSRF validation. The current SameSite=Strict choice can omit the cookie on that cross-site navigation; do not work around it with anonymous callbacks or SameSite=None. See [cookie navigation rules](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#samesitesamesite-value).

Keep any required trusted API credential handling separate from the browser interaction inside the same small auth module. The dashboard never asks for API keys or uses them as a fallback. PayPal OAuth is provider authentication, not an operator sign-in mechanism; add no staff OAuth/SSO flow, JWT access/refresh pair or authentication-provider abstraction.

## 5. One Submit, one outcome action

Use one payment-request resource and its target contract; remove the old execution endpoints rather than supporting both:

| Contract | Responsibility |
| --- | --- |
| POST /api/v1/payments | Submit: validate metadata/terms, persist request and attempt, create the PayPal order/subscription and return the request ID, attempt ID and selected presentation data directly. Reject an overlapping checkout request from the same operator; after its answer arrives, close all that operator's unfinished local checkouts and create fresh payment/attempt identities. |
| POST /api/v1/payments/{id}/checkout-outcome | Receive the selected SDK/return outcome with the exact attempt ID and its correlation proof. An approval runs the shared verify/complete function; cancellation/error records only sanitized browser context. Return the resulting local record directly. |
| POST /api/v1/payments/{id}/attempts/{attempt_id}/cancel | Explicit operator cancellation of the latest open, unclaimed attempt awaiting approval. Serialize with capture; block late approval. One-time cancellation is local because only our callback captures. This one-time-only action never cancels a subscription at PayPal. Local checkout closure for either product uses the close endpoint; neither previous state blocks a fresh payment. |
| POST /api/v1/payments/{id}/attempts/{attempt_id}/close | Freeze an unfinished local checkout as failed, without provider calls or financial reclassification. Failed results cannot be reopened. |
| GET /paypal/success | Local result/approval-return page. In redirect mode it validates correlation and initiates the authenticated outcome POST before displaying the result. GET itself never captures. |
| GET /paypal/fail | Local cancellation/error page. An initial authenticated redirect-cancel return initiates one non-capturing outcome POST before displaying the record; reopening an already recorded result is read-only. GET alone never changes state. |

Both Submit paths start a v6 SDK session from the user gesture and pass an asynchronous backend creation promise. One-time card payments keep the guest overlay; subscriptions use paypal-subscriptions in explicit popup mode, as selected by the operator. They share terminal approval/cancellation/error handling. Do not force the one-time short card form onto subscriptions, force desktop iframe mode, or add a redirect fallback. SDK handlers POST the exact order/subscription outcome before navigating to local result pages. Keep signed return_url=http://localhost:8100/paypal/success and cancel_url=http://localhost:8100/paypal/fail for provider-controlled navigation. A success URL must pass correlation and provider verification; it never proves collection by itself.

No separate Save -> Generate checkout -> Open PayPal actions, queued 202/operation-ID handoff or parallel complete/outcome endpoint. Read/report routes remain; refund, cancellation and explicit synchronization return their own direct responses. Update frontend and documented API callers to the new response contract in the same change; current response shapes have no compatibility guarantee. Remove obsolete endpoints rather than retain aliases, version adapters or an old async API alongside the replacement.

The outcome body cannot assert paid=true or supply authoritative amounts. Resolve the exact attempt, then check its request ID, provider order/subscription ID and correlation proof; never apply an old callback to whichever attempt is currently newest. For redirect callbacks use signed, time-limited state bound to that attempt and initiating operator. Use the existing signing/authentication machinery with a separate purpose; no token framework. Authenticate the operator and enforce CSRF on mutation POSTs. Restore identity/CSRF through the single initial /auth/me request before submitting a return outcome. If login expired, sign-in may restore the result page but must not replay an already submitted/failed mutation. An unclaimed initial return is distinct from a retry; expired/invalid callback state performs no mutation and creates no replacement checkout. Allow only fixed local return destinations.

Only an approval outcome for the currently open, unclaimed attempt can enter the verify/complete function. Error/cancel events never capture. Once the attempt is closed after an error/cancellation, a late approval callback cannot resume it or trigger capture. Concurrent outcome handling must serialize the attempt state. A provider mutation already sent cannot be undone by a later browser error; keep its actual/uncertain financial outcome and reservation. Treat arbitrary SDK error text as untrusted, potentially sensitive input: store a bounded safe code and local context, not raw payloads, customer/card data or a definitive financial failure without provider evidence.

## 6. State, duplicates and interrupted requests

Keep browser checkout state distinct from financial state without adding a generic state-machine framework. Persist only the states and transitions the selected product actually needs.

- Verified completed capture means collected. A provider-confirmed pending result remains pending. Definitive provider rejection means failed. A closed browser checkout is cancelled/abandoned, not proof of zero collection.
- A timeout, disconnect or database failure after a provider request leaves its existing mutation uncertain. The precommitted ledger entry preserves that uncertainty even if the result cannot be written. Read serialization must not misrepresent an interrupted in-flight action as a running background job.
- Record the provider-mutation boundary before dispatch. Failures before dispatch have no remote mutation to reconcile; after dispatch, do not infer rejection from an HTTP error, disconnect or missing final commit unless the provider gives definitive evidence. Separate read-only verification errors from capture errors, and never overwrite a verified completed record with a later browser/error callback. A failed order-creation response may also leave a provider order without a saved ID; keep that attempt uncertain rather than create another automatically.
- Use one stable submission key per submitted form/attempt and preserve its non-sensitive identity across the PayPal return and page reload. Same key plus different input is rejected. Disable concurrent clicks; also enforce server-side uniqueness/atomic claims so different keys cannot bypass the same existing request/attempt reservation. Do not deduplicate unrelated new requests merely by matching reference or amount: repeated legitimate payments may share them. Do not promise that idempotency identifies two genuinely separate submissions as one.
- Save only non-sensitive intent/submission identifiers in tab session storage before dispatch. Read-only lookup resolves a lost response; entering Create payment clears the saved identity and opens a blank form after outstanding requests finish; any saved-result lookup/closure must answer before enabling the next Submit. Reload never resends creation or capture.
- A repeated callback returns the stored result or explicit in-progress/uncertain state; it does not issue another capture. Claim a mutation once in a short transaction before contacting PayPal.
- Local form validation before contacting PayPal is not a payment attempt. After a PayPal attempt fails or is cancelled, end that checkout session and display failure/cancellation without automatically starting another. Do not mistake a browser/3DS error for proof of no collection; retain separate financial state.
- Only an explicit operator Submit creates a new independent payment/attempt. Old submission keys and callbacks remain non-executable; failed sessions are never resumed. Every new Submit gets fresh intent, submission and provider identities.
- Prior checkout/provider outcomes never gate the next new payment or subscription. A deliberate independent attempt does not establish that the previous provider operation failed or cancelled; keep any actual collection/subscription evidence and refund reservations intact.
- Reopening a recorded result page is read-only. Initial legitimate return processing may complete an unclaimed approval, but duplicate/replayed/expired callbacks cannot execute a second financial action. If the browser never returns, nothing automatically captures or updates that checkout.

No retry/backoff engine, automatic reconciliation, capture recovery or mutation replay. Explicit synchronization is read-only and updates provider/financial evidence without changing terminal checkout success/failed.

A creation/capture timeout may leave financial evidence uncertain. Close the operator checkout as failed, without falsely cancelling a provider agreement or deleting a financial reservation. This uncertainty cannot block a new independent operator Submit. Financial facts remain visible separately and refunds retain their existing safety rules.

Enforce zero implicit payment replays in every layer: HTTP transport/client retry settings, OAuth-error handling, SDK callbacks, frontend fetch/query libraries, network reconnect handling and process startup. Obtain/refresh OAuth before a mutation when needed; a rejected mutation must not be transparently resent after refreshing OAuth. The first capture of an approved attempt is the intended continuation of Submit, not a retry; a failed/timed-out capture must not be called again automatically. Apply the same no-automatic-retry policy to refunds and subscription cancellation.

## 7. Dashboard and retained functions

- Keep the RuTV design and show the same supported actions to every authenticated staff member. Submit starts the selected PayPal experience immediately; the operator enters card details only there. Remove the old intermediate action buttons and queue/status banners.
- Use three required fields: First name (first_name), Last name (last_name) and Agreement number (agreement_number). Keep amount/currency, billing terms and optional internal comments. These fields resolve the customer-information decision; do not add mandatory email, phone or billing-address fields to our dashboard. PayPal-controlled checkout collects any additional payer/card information its selected product requires.
- Preserve the current amount meaning explicitly: a one-time payment charges the entered amount once; period information does not multiply it. For a subscription it is the amount per billing interval, with the selected finite cycle count or explicit Until cancelled choice. Show those terms before Submit, apply cycle input only to subscriptions and retain existing supported interval/amount limits. Do not add tax, fee, installment-total or currency-conversion calculations.
- Validate first_name, last_name and agreement_number as non-empty, trimmed, bounded strings. Limit each name to 140 characters and their combined display name to 255. Preserve the exact name parts in immutable attempt terms and pass them through documented PayPal name fields; derive the combined client_name for local records and search. Agreement number is text: preserve leading zeros and non-numeric characters. It is not a unique payment identity; multiple legitimate payments/subscriptions may use the same agreement number.
- Persist the combined client name and agreement with the payment and make them available in payment/subscription records, relevant table columns, details, search and reporting. Update form labels, TypeScript types, backend schemas/models/serialization, validation messages and tests together. Replace external_reference in the target contract instead of retaining an alias, combined-field parser or duplicate reference field. No data migration is needed. Keep internal comments out of provider-facing descriptions and do not expose unnecessary client information in provider metadata or logs.
- Preserve non-card input on errors. Use the initiating request/callback response and a single local-record refresh for display. No status timer, stream or replacement transport.
- After any unsuccessful checkout, show Failed and Create a new payment. The button and main menu open a blank form after open requests finish; neither submits automatically. Do not reopen a failed hosted session.
- Restrict CSP to the PayPal script/frame/connect hosts required by the chosen product/environment. Keep frame-ancestors protection on the internal app. Do not loosen authentication, wildcard origins or log callback queries to make the SDK work.
- Keep subscriptions distinct: approval verifies subscription terms/state and never uses Orders capture. PayPal runs recurring billing. Without polling/webhooks, renewals and external refunds/reversals are visible only after explicit synchronization; show last verification time and incomplete coverage. Do not mark subscription approval as a completed first collection without evidence.
- Confirmed subscription responsibility: PayPal schedules and attempts recurring installments, handles its own failed-installment retries and sends the appropriate outcome emails. The payment service does not initiate recurring charges, retry failed installments, collect outstanding balances or send subscription outcome emails. Do not add a mailer, notification queue, webhook listener, scheduler or recurring-payment worker for these tasks.
- PayPal-managed subscription billing/retries are allowed and are outside the operator-only rule for service-initiated payment attempts. Do not disable subscription checkout merely because PayPal retries installments, and do not attempt to suppress those retries to satisfy the one-time flow rule. Select the product's ordinary documented billing settings; do not invent a custom billing policy. Notification behavior belongs to the PayPal account/product configuration, not this service; do not claim its actual email delivery has been verified without evidence.
- Enable subscription checkout and sale refunds without configuration gates; provider rejections remain visible. If the selected one-time presentation cannot serve recurring payments, record that separate product limitation; do not add vaulting/custom recurring billing or silently remove subscriptions.
- Refunds and subscription cancellation remain explicit operator mutations with reservations/idempotency. Provider permission errors are surfaced directly, without alternate-API fallbacks.
- Execute an explicitly requested import page/window within a bounded request. Persist its checkpoint only with the corresponding results; return its next cursor/coverage. Additional work needs an explicit request. No hidden continuation or unbounded full-history call.
- Client name and Agreement number are required for service-created payments. Future provider imports may lack these internal fields: keep them explicitly unassociated, display that fact and the provider payment identity, and never invent names/agreement numbers or match by amount/name automatically. This is a current import requirement, not historical-data compatibility; add no customer-management subsystem. Missing internal metadata alone does not invalidate an otherwise eligible collection for refund.

### Refund from the payments list

- On each eligible collected-payment row, place a clearly labelled Refund button immediately beside the payment amount. It acts on that individual payment, not on the client's aggregate balance or the subscription's nominal total. Show Agreement number separately. Clicking/keyboard-activating Refund opens the refund form without also triggering the row's detail-navigation handler.
- The form shows Client name, Agreement number, original payment date, original amount/currency, already refunded amount and maximum currently refundable amount. Let the operator enter a positive partial refund or choose the full remaining amount, review it and explicitly confirm. Currency is fixed to the original ILS/USD/EUR payment; money is validated with Decimal and serialized as strings. No new checkout or card entry is involved.
- PayPal documents full/partial refunds within 180 days of the original payment/capture date. Use the original verified provider payment timestamp, never local request creation, subscription start or last synchronization/update time. Calculate refund_deadline as that timestamp plus 180 days in UTC and reject at/after it; do not round age to local calendar days, extend the limit or introduce a configurable refund-window policy. This conservative local cutoff does not promise acceptance up to the last instant: PayPal makes the final eligibility decision. Sources: [PayPal refund time limit](https://www.paypal.com/us/cshelp/article/how-do-i-issue-a-refund-help101) and [capture refund integration](https://developer.paypal.com/checkout/refund-payment).
- Compute refund eligibility in one backend function shared by payment-list serialization and refund execution. Return can_refund, refundable_amount and refund_deadline with the payment row. The UI uses these values and checks the deadline when rendering/opening the form; it must not duplicate the provider eligibility policy or add polling. Refund submission always revalidates against the current server clock and balances, including when a previously opened page/form has become stale.
- Show a rectangular Refund button beside each collection amount with 16px spacing. Enable it with the primary button background only when the backend confirms eligibility and its known refund deadline is still open; disable it with a grey background when ineligible or while work is busy. Do not show refund actions for refund/adjustment rows. Unknown or malformed eligibility/deadline information never enables the action. A date inside 180 days is necessary, not a guarantee of provider acceptance; listing the page itself makes no per-row PayPal requests.
- A partially refunded collection remains eligible for its remaining amount; do not require its latest provider status to be literally COMPLETED if that product reports PARTIALLY_REFUNDED. Distinguish a pending collection from an originally collected payment with a pending partial refund. Reserve that refund's amount and compute eligibility from the remaining balance.
- List/form amounts reflect the last verified local information, with its verification time. Without webhooks/polling, an external refund or restriction can make them stale. Do not promise a globally current balance or assume a provider detail response contains a cumulative refund total unless the selected API documents it. Explicit read-only synchronization may refresh the available facts; if they leave the remaining balance unknown, disable refund rather than guess. A provider rejection is displayed directly, with no alternate route or automatic resubmission. An extra read-before-write cannot eliminate an external race and is not a required verification subsystem.
- The refund limit is at most the original collected payment amount and, after earlier partial refunds, at most its remaining refundable balance. Subtract completed refunds and pending/uncertain refund reservations; account for verified reversals or provider restrictions without permitting over-refunding. Never refund more merely because the operator changes the input or uses a new request key. Refunds use the original collection currency and never include uncollected future subscription installments.
- Confirm uses the single direct refund action, POST /api/v1/transactions/{id}/refunds. Reuse the shared eligibility/amount checks, atomically reserve the requested amount before the outbound mutation and send one provider request with its stable idempotency key. Recheck concurrent reservations without holding a database transaction over provider HTTP. Duplicate confirmation returns its recorded result; it never issues another refund. There are no role-specific branches, approval chains or automatic retries.
- Always submit the exact amount/currency the operator confirmed, including for Full remaining; do not omit the provider amount or silently recalculate a different refund. Bind the submission key to that immutable amount. If a concurrent refund reduces the available balance, reject the stale confirmation and require a new explicit review, rather than changing or splitting it automatically.
- Persist and display the provider's actual refund status. Pending/uncertain refunds continue to reserve their amount until explicitly verified; accepted is not the same as completed. Update the affected local row once from the direct response: disable Refund when no balance/window remains, or allow another explicitly initiated partial refund if still eligible. On failure, display the result without automatically resubmitting. If the operator deliberately starts another refund, revalidate eligibility and the previous outcome first.
- Subscription installments are refundable only as individual collected payments through the selected product's supported/verified refund API. A subscription agreement itself is not a refundable collection. Do not enable an unsupported sale-refund route or use an alternate transfer/send-money method as a fallback. A refund does not cancel the subscription; keep cancellation a distinct explicit action.

## 8. Currency rule: ILS, USD, EUR

ILS, USD and EUR are the only supported currencies; default ILS. Reject GBP, CAD, AUD and every other code for new processing. One backend allowlist/type drives validation and options; frontend controls consume those options rather than maintaining another hardcoded list.

Apply the rule to payment/subscription creation, plans, capture verification, refunds, filters, trusted API callers, imports and explicit synchronization. Verify the provider currency against the saved terms; never substitute a default or perform conversion. Keep two-decimal validation, per-currency totals and unknown-fee semantics.

For future explicit imports of mixed-currency provider results, process only supported entries and report exclusions/coverage honestly. A specifically requested unsupported-currency resource returns unsupported-currency. There are no pre-existing unsupported-currency records requiring preservation, special inspection paths or migration. Do not create records for unsupported currencies. No compatibility processing, archive UI, currency conversion or dynamic currency registry.

Remove rather than configure a dormant retry path. Keep idempotency solely to reject duplicates/return saved results, not as permission to replay a failed request.

- Queue-producing helpers and queued 202 responses; operation-status endpoints/polling; queue-only Attention components, banners, types, tests and API documentation. Display actual failed/uncertain outcomes on the new payment records.
